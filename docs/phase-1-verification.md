# Проверка рабочего каркаса Прямогорода
Дата: 11 ноября 2026. Этап 2: аудит и фиксация первого этапа.

## Вывод
Каркас пригоден для дальнейшей разработки карты и первого нового игрового модуля в локальной среде. Проверенные основные сценарии работают. Это не заключение о готовности к публичному production: вход с восстановлением, физическая камера QR, готовые сценарии, художественный контент и авторитетная экономика игровых модулей остаются отдельными задачами.

Дополнительно выполнены HTTP-проверка собранного сервера, запросы целостности SQL и автоматизированные действия в браузере.

Новые игровые механики, библиотеки, движки и художественные материалы не добавлялись. Цены, формулы наград, дружба и большой тестовый баланс Мэйку не менялись.

## 3. Безопасность: что проверено
### Одноразовость и атомарность
- Сервер блокирует пользователя и строку токена в транзакции.
- В qr_activations token_id уникален; коллекция уникальна по пользователю и дизайну.
- 12 конкурентных запросов первого QR: один 200 и одиннадцать 409.
- Два запроса QR повторного дизайна: один 200 и один 409; кошелёк +10, журнал содержит одну строку.
- Два пользователя одного токена: один успех.
- Искусственная ошибка BEFORE INSERT в user_scenes откатывает использованность токена, активацию, коллекцию, первое здание, район и сцену.
- Искусственная ошибка BEFORE INSERT в coin_ledger откатывает предшествующее изменение кошелька и активацию. Тот же токен затем успешно погашается один раз.
- Временные триггеры удалены в finally; SQL-проверка после прогона обнаружила 0 оставшихся тестовых триггеров.
- Сообщения verification injected failure в логе ожидаемы: это намеренная проверка отката, не непойманный дефект приложения.

### Источник награды и доступ
- Дополнительные поля reward, designId, buildingId, userId в запросе погашения отклоняются с 400.
- Дизайн, эффект и здание вычисляются сервером по хешу токена и связям каталога; пользователь берётся из сессии.
- Реальный, не тестовый токен принят production-конфигурацией; его здание и дизайн совпали с хранимыми данными.
- Неизвестный токен даёт 404, истёкший — 410, мир не меняется.
- GET и PUT сохранения закрытого здания дают 403. JSON с unlocked=true не открывает его.
- Запрос изменения /api/world отсутствует (404). Клиентские массивы зданий и баланс не принимаются сервером.
- Сохранения двух пользователей изолированы даже при открытом у обоих одном здании.
- Две записи revision=0 не могут обе победить: один успех, один 409.
- Изменение монет в JSON модуля не меняет городской кошелёк.
- Без сессии погашение даёт 401; чужой Origin — 403.
- Сессии хранятся по хешу; production-cookie имеет HttpOnly, SameSite=Strict и Secure.
- Dev-маршруты отсутствуют в production (404), тестовый QR отвергается (403). Отдельный реальный процесс подтвердил выключение dev-маршрутов при NODE_ENV=production, даже с DEV_TOOLS=true.

Граница утверждения: пользователь способен изменить отображение в собственном браузере, но это не даёт серверного открытия или награды. Это не полный пентест. QR — предъявительский токен; проверка заказа/покупателя и внешние API не входят в каркас.

### Целостность данных
В основной базе и новой тестовой базе выполнены SQL-запросы:
- расхождение wallets.balance и суммы coin_ledger: 0;
- несовпадение пользователя/дизайна активации и токена: 0;
- первое здание пользователя отсутствует среди его открытых: 0;
- открытое здание без своего открытого района: 0;
- реестр: 4 / 16 / 16 / 256;
- 001_world.sql зарегистрирована с контрольной суммой длиной 64 символа.

## 4. Исправленные проблемы
### Потеря несинхронизированной локальной копии Мэйку
Подтверждение кодом: load() ранее всегда выбирал remote.save.data.progress перед scoped. После ошибки отправки локальный прогресс мог быть новее серверного и молча заменялся при следующем входе.

Исправление:
- Локально хранится контрольная точка последнего подтверждённого сервером прогресса и его revision.
- Если локальные изменения не отправлены, а серверная ревизия та же, используется локальная копия и повторяется отправка.
- Если сервер тоже изменился, локальная копия остаётся, автоматическая запись останавливается.
- Старые копии без контрольной точки обрабатываются консервативно; при неоднозначности требуется явное действие.
- Совпавший с сервером результат запроса с потерянным ответом распознаётся без ложного конфликта.
- Перед явной загрузкой серверной копии сохраняется резервная локальная.
- Загрузка во время активного сохранения откладывается; ошибки кнопки загрузки отображаются.
- Ошибка отправки не заменяет более свежие уже ожидающие данные старым снимком.

7 регрессионных тестов проверяют выбор данных, конфликт ревизий, прежний формат копии, потерю ответа и большой баланс. Они проверяют чистую логику выбора; полный сетевой обрыв браузера во время каждого возможного шага адаптера не моделировался.

В браузере проверены консервативный конфликт прежней копии без контрольной точки, явное сохранение и последующий вход с текстом «Сохранение Мэйку загружено».

### Опасный запуск интеграционных тестов без отдельной базы
До исправления серверный тест мог использовать DATABASE_URL по умолчанию основной локальной базы.

Теперь до тестовых записей требуется явный DATABASE_URL и фактическое имя базы с суффиксом _test. Запуск без переменной намеренно завершился с кодом 1; количество пользователей основной базы до и после совпало. Для каждого тестового блока создаётся новый Fastify-экземпляр, чтобы лимит запросов одного прогона не смешивался с соседними тестами.

## 6. Оставшиеся ограничения и риски
1. Гостевая cookie на 30 дней, без восстановления входа и переноса аккаунта. Для внешнего выпуска нужен механизм входа.
2. Экономика Мэйку остаётся клиентской. PUT модуля хранит JSON, а не проверяет каждый игровой ход. Городские награды защищены отдельно. До подключения новых наградных механик нужны серверные команды и проверка схемы прогресса конкретного модуля.
3. moduleEvent сохраняется на сервере, но текущая доставка на клиенте устраняет повторы только в пределах сеанса JavaScript. Сейчас обработчик не выдаёт наград. Перед выдачей будущих наград по событию понадобится долговечная идемпотентная обработка.
4. Импорт каталога — инструмент разработки. Перенос уже открытого здания между районами нужно сопровождать отдельной миграцией пользовательских открытий; текущий импорт не является такой миграцией. Сейчас проверенная целостность не нарушена.
5. Две навигации в модуле Мэйку сохраняют прежний интерфейс. На низком экране комната требует прокрутки; полный мобильный UX-прогон в это техническое заключение не входит.
6. Локальные копии зависят от localStorage. Очистка браузера удалит несинхронизированные данные; автоматического слияния конфликтующих игровых прогрессов нет.
7. Значения окружения и пароль в примере предназначены для локальной разработки; публичное размещение требует своих секретов, HTTPS, роли БД с нужными правами и резервного копирования.
8. При первом входе после этого исправления прежняя локальная копия без контрольной точки может вызвать консервативное предупреждение. Её не удаляют и не сбрасывают.

Не проверены: Docker Compose (Docker отсутствует), физическая камера, Safari/Firefox на телефонах, внешнее HTTPS-развёртывание, нагрузка реальных пользователей, восстановление после потери питания и резервной копии, полный пентест. Работа BarcodeDetector на физических устройствах не объявляется подтверждённой.

## 9. Точка фиксации и готовность следующего этапа
git rev-parse --show-toplevel в рабочей папке завершился сообщением «not a git repository». Репозиторий не инициализировался, коммиты и теги не создавались. Существующие файлы не откатывались; до изменения сохранены копии тестового файла и адаптера в отдельной рабочей папке Codex.

Предлагаемая точка фиксации после создания/подключения Git: коммит «Verify phase 1 and preserve unsynced Meiku progress», тег phase-1-verified. Контрольные суммы в соседнем manifest фиксируют проверенные исходники без .env, node_modules, данных БД, сборок и графических исходников.

Можно переходить к карте и одному новому модулю, сохраняя ID каталога. Перед изменением распределения зданий утвердить миграцию, а перед наградами нового модуля — серверные команды и идемпотентность. Разработка следующего этапа в рамках аудита не начиналась.
